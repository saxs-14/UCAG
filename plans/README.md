## Rejected (checked, not implemented)

**BursariesPage's filter-triggered list remount** — flagged during the audit, but `components/bursaries/BursariesPage.tsx:133-135` documents it as deliberate: *"key ties this list to the active filters -- changing a filter remounts it, replaying the rise-in/stagger entrance so the list visibly 'refreshes' instead of silently swapping content."* No plan written.

**`.animate-rise-in`'s pervasive 420ms duration** — used almost everywhere in the app, technically over AUDIT.md's generic UI budget, but it's this app's own deliberately-chosen signature entrance timing after 3-4 real design passes with direct owner feedback each time. Flagged during the audit but not turned into a plan — only worth touching on explicit request for a sitewide snappier feel, not as a mechanical "fix."

## Recommended execution order

Run in numeric order, 001 → 016. Severity order and dependency order happen to coincide here:

- **004 must run before 008, and 008 before 010.** All three touch the same `hover:`/`active:` className strings on overlapping elements (SubjectCombobox's clear button, the Apply CTAs, the chat FAB/send button): 004 renames `hover:` → `hover-fine:`, 008 adds missing `active:` states, 010 aligns the resulting magnitudes. Running them out of order will make each plan's "current code" quote not match what's actually on disk — each plan's Boundaries section says to STOP and report rather than improvise if that happens, so worst case is a wasted dry run, not a bad edit, but running in order avoids that entirely.
- **011 should run before 014** (both touch `SubjectForm.tsx`'s elective-slot className). Plan 014 explicitly handles either order (it describes both the pre- and post-011 shape of the code), so this is a soft preference, not a hard blocker.
- Everything else (001, 002, 003, 005, 006, 007, 009, 012, 013, 015, 016) touches disjoint files/lines and can run in any order, including in parallel across separate agents/worktrees.

## Notes

- No motion library exists in this repo (plain CSS `@keyframes`/`transition`, no Framer Motion/GSAP/React Spring) — none of these plans introduce one.
- Plan 001 introduces this repo's first `--ease-out`/`--ease-in-out` CSS custom-property tokens (in `app/globals.css`'s `@theme` block). No other plan in this set currently depends on them, but future motion work should prefer them over hand-typing new cubic-beziers.
- Every plan's mechanical verification includes `npm run typecheck`, `npm run lint`, and `npx vitest run` (full suite, 288 tests as of commit `1522b53`) — none of these changes should affect any of those, since the existing test suite doesn't cover animation/motion behavior directly. A failure in any of them after applying a plan means something drifted from what the plan expected; stop and diff against the plan's "current code" quotes before proceeding.
